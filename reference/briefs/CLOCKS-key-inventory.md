# FluidWallpaper -- CLOCKS key inventory (read-only)

Source of truth: `src/ui/keys.inc` (392 rows: 366 KEY_SLIDER + 26 KEY_CHECK), cross-checked against `src/fluid.h` struct initialisers for defaults and `src/cycle.cpp` / `src/animators.h` for the existing time-varying machinery. Generated by parsing keys.inc programmatically (script: `gen_inventory.py`/`gen_groups.py`/`gen_markdown.py` in this scratchpad) rather than transcribed by hand, to avoid errors at this row count. No repo files were built, rendered or edited.

Look codes: **F** = fluid (WE), **A** = liquid_acid (oil-on-ink), **I** = ink (ink-in-water, shared by `style=ink` and `[liquid_acid] ink_mode=water`).

## 1. Every numeric key

366 KEY_SLIDER rows (continuous, integer-count, and slider-shaped enums together) + 26 KEY_CHECK rows (booleans). Defaults are the `src/fluid.h` struct-initialiser value for that field (not necessarily what a shipped preset/ini overrides it to -- e.g. `sim_res`/`dye_res` default to 256/1024 in the struct but AGENTS.md documents the *live* WE-parity values as 256/4096, set by ini). "Hot-swappable" answers: does the renderer read this field fresh every frame (Settings-window edits already apply live, per AGENTS.md), or does it only take effect at resource creation / a PSO compile / a swapchain reconfigure?

## 4. Existing time-varying machinery (for a per-key slow clock to hook into)

### Cycle director stage overlay (src/cycle.cpp)

- **Tick rate**: `CycleTick(FluidRenderer&, float dt)` (`src/cycle.cpp:1149`) is called once per rendered frame from the main loop (`src/main.cpp:3103` and `:3812`), not on a fixed timer -- `dt` is that frame's sim delta, so the director's clocks run at display fps (`fps_limit`).
- **Stage overlay composition**: `Compose(int i, const FluidConfig& live, FluidConfig& out, float& peak, int& gamut)` (`src/cycle.cpp:385`) builds a fresh `FluidConfig{}` (code defaults), loads the stage's optional `basePath` ini over it, then the stage's own `path` ini over that, then force-copies the SHELL keys (`sim_res`, `dye_res`, `fps_limit`, `mirrorSecond`, CLI debug flags, `hdr_peak_nits`, `gamut`) from the live config -- stage inis can never touch those. `[hdr] peak_nits`/`gamut` in an ini override the user's own setting if present (`:405-415`).
- **Applying it in memory**: `ApplyStage()` (`src/cycle.cpp:485`) and `FinishLerp()` (`:778`) both call `Compose()` then `r.Config() = c;` -- a direct whole-struct overwrite of the live `FluidConfig`, done only at a black frame (stage entry) or at the end of a lerp. Nothing is written to disk (`PersistCurrent()` only writes which stage index is current, `:425`).
- **CycleStageBase()** (`:1652`, exposed via `animators.h:76`) re-runs `Compose()` against the CURRENT (or, mid-lerp, the target) stage without touching live Config -- this is what "dirty" and Revert are measured against, and is the closest existing hook for "what is the stage's own baseline for key X".
- **Fluid-to-fluid transition**: `BeginLerp()` (`:754`) computes a hue-bridge angle (`CommandHueShift`) and enters `CYCLE_LERP`; each tick `LerpLook()` (`:311`, listed float fields only -- ~40 of them, e.g. `densityDissipation`, `curl`, `postHue`, `hueCenter`, `hsStep`...) linearly interpolates FROM `s_from` TO `s_target` by `Smooth(t)`; `FlipDiscrete()` (`:360`) flips bools/ints/the splat-colour array at the lerp midpoint (t>=0.4). This is a ready-made pattern for "ramp a numeric key over N seconds" but it is purpose-built for whole-stage transitions, not a per-key independent clock.
- **Journeys**: `AttachJourney`/`JourneyUpdate` (`:441`, called from `CycleTick` `CYCLE_DWELL` branch at `:1170`) drive fluid-stage parameter ramps DURING a dwell -- the closest existing "per-key clock during steady state" mechanism, declared as a stage type per `animators.h:17-20` (journeys run only in DWELL; Config == composed base otherwise).
- **Scheme cross-fade**: `CYCLE_SCHEME` phase (`:1228`) ramps four `LiquidAcidConfig` amounts (`filmHue2Amt`, `filmHue3Amt`, `shadowTone`, `highlightToneAmt`) down then up via `SetAmts()` over `schemeRampSec` (default 2s, `cycle.h:129`) -- another existing multi-key ramp, scoped to exactly those 4 fields.

### Other own-clock mechanisms not on the animator enum

- **shadow_tone's own clock**: NOT `AnimatorTime` -- uses raw `m_time - m_toneT0` directly (`src/fluid.cpp:6034`, gate function `ShadowToneGate`), where `m_toneT0` resets to "now" the moment the tone keys go from all-zero to nonzero, or after a >1s gap without a constant upload (e.g. director was on another look) -- logic at `:6020-6033`. Governed by `shadow_tone_period`/`shadow_tone_fade` (on/off crossfade), independent of any Freeze() call.
- **Palette start hue** (one-shot, not a running clock): `ApplyPaletteStart()` `src/fluid.cpp:2242` -- fires once at app start (`:140`) and once per cycle stage entry (`cycle.cpp:498`, "here, at black, never on the no-black scheme change"), inverts the anchor-warp to land the palette clock's phase on `palette_start_hue` (or a random anchor-weighted draw at -2).
- **Burst** (temporary kick, not a standing clock): `FireBurst()` `src/cycle.cpp:809` calls `AnimatorKick(ANIM_PALETTE, ...)` (`animators.h:61`, impl `cycle.cpp:1537` -> `FluidRenderer::AnimatorKick` `src/fluid.cpp:2161`) to smoothstep the palette clock forward 90-200deg onto the nearest proven anchor over `burst_sec`; the offset this leaves behind is permanent (the clock resumes drifting from the landing spot), so it is a one-time nudge, not a periodic mechanism. Watched for completion in `CycleTick` at `:1156-1163`.

### What a "per-key slow clock" could hook into

There is no existing generic "animate any Config float over time" primitive -- every mechanism above is either (a) a derived, never-persisted clock hard-wired to a specific handful of fields (palette hue, hue2 wobble, rig, hue-shift angle, shadow-tone gate), or (b) a whole-stage transition (`LerpLook`, `CYCLE_SCHEME`) that ramps a fixed, hand-picked list of fields together and writes the result into live Config. The closest structural precedent for "one independent clock per arbitrary key, written into Config" is a **Journey** (`AttachJourney`/`JourneyUpdate`, DWELL-only, per `animators.h`'s BASE-vs-LIVE split under "(b) WRITTEN into Config"), and the closest "read every frame, never touches Config" precedent is the `AnimatorTime(a)`-driven derived clocks -- either would need a new registry keyed by keys.inc's own `(pointer, min, max)` metadata (already surfaced to the UI via `ui_model.h`'s `KeyRow`) to generalise beyond the current fixed field lists.

### R1 (high) Master clock m_time is a float: 12.5% fast after ~9 h, frozen after ~36 h of rendering at 144 fps

- Where: `src/fluid.h:2093`; seen by 10 reviewers
- Trigger: The owner leaves the wallpaper running at 144 fps. Fullscreen pauses don't advance m_time, but cycle warm-up sub-steps do. After about 36.4 h of rendered time, m_time = 131072.0 and stays there. In an oil (liquid_acid) stage, the palette stops turning and the rig lamp, lens null point, lid ghosts and pixel-shift orbit hold their last position on the QD-OLED for the rest of the session. The oil blobs keep being pushed by the last 64x36 velocity readback, which never refreshes. On a WE stage, the first mouse movement stops the wanderers permanently and the auto-pause governor stops measuring. Only a restart of the exe recovers.
- Checked: The claim holds. I checked the code and the float arithmetic. m_time is a float (fluid.h:2093). It is only ever changed by `m_time += dt` (fluid.cpp:1932 Frame, 2136 SimOnlyStep), and nothing resets it on suspend, resume or reattach (grep found no other assignment). In the live loop dt is the measured QPC interval (main.cpp:4045), clamped to 1/30. Under vsync at 144 Hz that is about 6.94 ms. The float spacing above 2^17 s (131072 s) is 2^-6 = 0.0156 s. Any dt below half of that (0.0078 s) rounds away, so m_time stops on every normal frame. It only creeps forward on jitter frames longer than 7.8 ms and on the cycle warm-up SimOnlyStep sub-steps. It does not stop dead, but it runs roughly 10x or more slow, which in practice is frozen. Between 2^15 s (about 9.1 h) and 2^17 s, every 6.94 ms dt rounds up to 7.8 ms, so all clocks derived from m_time run 12.5% fast. That part is also correct. ...
- Fix: Smallest fix that keeps the baselines bit-identical: add `double m_timeD` and do `m_timeD += dt` in both places. - Keep the float as the public clock while it is small, e.g. `m_time = (m_timeD < 8192.0) ? m_time + dt : (float)m_timeD;`. Every --shot run and identity baseline is far below 8192 s, so it gets exactly today's float sum, and the "enabled=0 bit for bit" cycle path is unchanged. - This alone stops the freeze (the double never sticks), but the float shader values are still coarse at large t. - For the long run, make m_animFrozenAccum a double and have AnimatorTime return (float)(m_timeD - accum). Change the `m_time - m_lastX >= period` gates and m_lastInteraction to doubles. Turn the shader uploads (LA_TIME, c[9], the mirror time, ink p2.w) into a wrapped float, either fmod(m_timeD, a large period) or a rebase at a cycle black point so the wrap is never visible. What it could break: - A plain float-to-double switch, without the small-t float path, changes rounding from the first frame. Every --shot identity hash (HDR on included) would then need re-baselining. - A wrap of a shader time that is not at a black point shows as a one-frame grain, speckle or seam jump. - Cycle code that stores AnimatorTime values (cycle.cpp:1047 clockEnd) must use the same type as AnimatorTime, or kick landings drift. - PaletteSyncTo-style assignments (fluid.cpp:2651 `m_animFrozenAccum[0] = ...

- Fix: Smallest fix: in Shutdown(), change line 2740 to `if (m_queue && m_fence && m_fenceEvent) WaitForGpuIdle();`.
